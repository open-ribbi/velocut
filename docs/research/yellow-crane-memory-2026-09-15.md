# 黄鹤楼真实项目内存复测（2026-09-15）

结论：最终工程本身没有在本次有限时长复测中表现出持续增长的内存泄漏。实际内存负担主要来自图形进程，以及历史中的重复场景描述。不能用 JS 堆大小代表完整浏览器内存，也不能据此排除原来 41 分钟建模过程中的临时网格、截图、插件服务或 Codex 界面峰值。

## 数据来源与环境

- 从任务 **Connect to local Velocut editor** 找到真实 `project-final.json`，并从 Codex 原浏览器的 localhost:5173 IndexedDB 只读副本提取对应项目的文档和历史。原浏览器数据库未被打开写入，原项目未被修改。
- 项目 **黄鹤楼 · 建筑重建与组装**，ID `pmu2avnc5p4n6`；文档 287,389 字节，1280×720、30 fps、138 秒。
- **1 个 3D 素材**，190 个原生构件、18 个分组；22 个场景片段共享该素材，另有 44 个文字片段，合计 66 个 clip。不能按“22 个独立 3D 场景”估算此项目。
- 原始历史 119 条，序列化为 34,996,027 字节（33.4 MiB）。历史 head 与保存的最终项目逐字段完全一致。
- 重放代码基线 `f9b811f`，生产构建。macOS，Apple M3 Max、64 GiB 内存，Chrome 153.0.8010.36，原生 ANGLE Metal，未使用 SwiftShader。
- 新建隔离浏览器 profile，载入真实文档和历史；打开导演台、以原任务使用的 4× 完整播放两轮、跨章节跳转、执行三次场景观察并重开项目。
- 内存使用 Chrome CDP 的 `Runtime.getHeapUsage` 和 macOS `footprint`。下表总量是该隔离浏览器整组进程的 physical footprint，包含浏览器、GPU、renderer 和辅助进程。GPU 列是 GPU **进程**的 footprint，不等于纯显存。
- 稳态点显式请求 GC，用来区分可回收临时对象与仍被引用的对象；播放点每约 5 秒采样且不强制 GC。采样峰值不是整个原始建模过程的绝对峰值。

## 真实历史下的测量

单位 MiB。

| 状态 | 主页面 JS 堆 | GPU 进程 footprint | 浏览器整组 footprint | 采样前 GC |
| --- | ---: | ---: | ---: | --- |
| 加载后、GC 前 | 77.3 | 733.7 | 1382.3 | 否 |
| 载入后暂停 | 72.3 | 216.9 | 582.9 | 是 |
| 导演台显示完整楼体 | 81.6 | 567.6 | 963.0 | 是 |
| 第一轮完整播放后 | 81.8 | 225.5 | 640.6 | 是 |
| 第二轮完整播放后 | 81.9 | 219.4 | 614.1 | 是 |
| 三次场景截图后 | 82.5 | 233.7 | 642.7 | 是 |
| 重新加载后 | 72.3 | 207.5 | 585.1 | 是 |

播放期间采样到的整组进程占用最高约 1198 MiB，首次载入的 GC 前采样为 1382 MiB（约 1.35 GiB）。第一、第二轮播放结束后分别回落到约 641 MiB 和 614 MiB；三次截图后约 643 MiB，重开后约 585 MiB。没有单调累积至数 GiB 的趋势，但此测试时长不能证明长期运行不存在泄漏。

空编辑器首次启动也出现明显的图形初始化临时占用，因此不能把加载瞬间 GPU 总量全部归因于黄鹤楼几何。更稳定的对照是相同项目、相同状态下 JS 堆与 renderer 占用的差异。

## 历史记录对照

三个运行使用相同模型：

| 条件 | 历史节点 | 载入暂停时 JS 堆 | 导演台 JS 堆 |
| --- | ---: | ---: | ---: |
| 原始完整历史 | 119 | 72.3 | 81.6 |
| 只保留当前状态的对照副本 | 1 | 10.4 | 19.6 |
| 119 条历史，仅共享重复的 spec 字符串 | 119 | 14.0 | 23.2 |

原始历史中，snapshot 的场景描述合计约 30.5 MB，但只有 **7 份不同描述**，合计约 1.77 MB。字符串共享实验保持全部历史节点及当前工程内容不变，主页面堆减少约 58 MiB（约 81%）。这是隔离副本的诊断实验，尚未修改产品的历史实现；重开副本后仍按现有格式恢复，堆回到约 72 MiB。

## 建议优先级

1. **历史存储去重和加载时共享。** 先共享不可变 scene spec，再考虑 checkpoint＋差异记录。此案例已经证明有实际收益，也能缩小原始 33 MiB 历史文件及加载临时缓冲。
2. **图形内存观测和预算。** 分别记录渲染目标、阴影贴图、VideoFrame、纹理和场景编译器的数量/尺寸，区分使用中、缓存、等待释放。控制预览分辨率及缓存保留量，基于真实数据决定上限。
3. **记录建模时的峰值。** 本次覆盖最终项目、原始历史和典型播放/观察操作。原任务中的模型生成进程、MCP 响应、截图附件及 Codex 对话渲染需要在实际编辑期间单独采样，不能从最终项目反推。
4. 创作能力仍缺显隐/缩放组装动画、更多网格原子操作、视频导出任务闭环，以及完整项目/资源备份与传输。这些与本次内存诊断分开推进。

没有合入前一轮 CPU 优化实验。相关未完成变更已存入本地 `artifacts/performance/parked-experiment`，本轮产品代码保持原基线。

## 复现与产物

从 `web/` 运行，需已安装 Chrome，且已构建生产 Studio。`footprint` 采样仅支持 macOS。

```sh
node scripts/extract-project-memory-fixture.mjs <原浏览器的IndexedDB目录> '<项目名称>' <本地fixture目录>
node scripts/profile-project-memory.mjs <fixture目录> <输出目录>
node scripts/profile-project-memory.mjs <fixture目录> <对照输出目录> without-history short
node scripts/profile-project-memory.mjs <fixture目录> <共享实验输出目录> with-history short intern-experiment
```

提取工具只复制 `http_localhost_5173.indexeddb.*`，只导出指定项目的 ydoc/history，不导出设置或凭据。二进制通过文件下载保存，不经 `Array.from` 展开传输。诊断脚本使用临时浏览器，并在退出时关闭。

原始 fixture、逐次 footprint JSON 和三组测量位于本地 `artifacts/performance/yellow-crane/`，不随源码提交。

最终项目 SHA-256：`f8b6675b6bf846b03e82673678cbfc94ad6c20f445e0add286e519cb15105e06`。

完整快照、命令、分支和节点 ID 的往返比较一致。新数据保存在独立的 compact-v1 键下，旧格式值保留作恢复副本，因此“活动保存数据缩小”不代表现有磁盘空间立即释放。GPU／总进程内存也不能套用 JS 堆的下降百分比。复测产物在 `artifacts/performance/yellow-crane/implemented-sharing/`。
